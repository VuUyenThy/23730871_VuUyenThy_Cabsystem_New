# TEST SCENARIO DISCOVERY PROMPT

Tôi đang thực hiện thiết kế Test Case cho một hệ thống phần mềm.

Tôi sẽ cung cấp cho bạn:

1. **SRS.md (Software Requirements Specification)**
2. **foder API Document**
3. **Test Case Template (CAB_Test_Cases.xlsx)** do giảng viên cung cấp.

## Mục tiêu

Hãy đọc và phân tích toàn bộ SRS và API Document để **gợi ý danh sách Test Scenario có thể kiểm thử**.

Lưu ý:

- Đây chỉ là bước **gợi ý Test Scenario**.
- Chưa tạo Test Case.
- Chưa tạo file Excel.
- Tôi sẽ là người xem xét và quyết định Scenario nào thực sự sử dụng.
- Không tự ý coi tất cả Scenario được đề xuất là bắt buộc phải test.

## Nguyên tắc

Chỉ dựa trên thông tin có trong:

- SRS
- API Document

Không tự tạo requirement hoặc business rule.

Nếu phát hiện thông tin mâu thuẫn giữa SRS và API Document, phải chỉ ra.

Nếu có thông tin chưa rõ, ghi "Cần xác nhận".

---

# 1. Phân tích SRS

Đầu tiên xác định:

- Module
- Function
- Use Case
- Requirement
- Business Rule
- Validation
- Exception Flow
- Actor
- Permission/Role
- Data Entity

Sau đó dựa trên những thông tin này để đề xuất Test Scenario.

---

# 2. Phân tích API Document

Đối với mỗi API, xem xét:

- HTTP Method
- Endpoint
- Authentication
- Authorization
- Path Parameter
- Query Parameter
- Header
- Request Body
- Required fields
- Optional fields
- Data Type
- Format
- Enum
- Min/Max
- Validation
- Response
- HTTP Status Code
- Business rule
- Error handling

Dựa vào đó đề xuất Test Scenario phù hợp.

---

# 3. Các hướng tìm Test Scenario

Khi phân tích mỗi Function / Use Case / API, xem xét các nhóm sau:

### A. Functional Scenario

- Chức năng hoạt động bình thường
- Các flow chính
- Các flow phụ
- Các alternative flow
- Các exception flow

### B. Positive Scenario

- Dữ liệu hợp lệ
- Điều kiện hợp lệ
- Flow thành công

### C. Negative Scenario

- Dữ liệu không hợp lệ
- Điều kiện không hợp lệ
- Hành động không được phép

### D. Boundary Scenario

Nếu tài liệu có giới hạn:

- Minimum
- Maximum
- Dưới minimum
- Trên maximum
- Giá trị gần boundary

### E. Missing Data Scenario

- Thiếu required field
- Empty field
- Null
- Missing parameter
- Missing request body

### F. Error Data Scenario

- Sai data type
- Sai format
- Sai enum
- Sai value
- Resource không tồn tại
- Duplicate data
- Validation error

### G. Authentication / Authorization

Nếu hệ thống có:

- Chưa đăng nhập
- Đã đăng nhập
- Role không có quyền
- Role có quyền
- Token/session không hợp lệ
- Token/session hết hạn

Chỉ đề xuất nếu tài liệu có liên quan.

### H. Business Rule

Kiểm tra các điều kiện nghiệp vụ được quy định trong SRS.

### I. Data State

Nếu phù hợp:

- Data tồn tại
- Data không tồn tại
- Data đã được sử dụng
- Data đã bị xóa
- Data đang ở trạng thái khác
- Duplicate data

Chỉ đề xuất khi có cơ sở trong tài liệu.

---

# 4. Không tạo Scenario trùng lặp

Nếu hai Scenario có cùng mục tiêu kiểm thử, hãy:

- Gộp chúng
- Hoặc chỉ ra rằng chúng bị trùng

Không tạo nhiều Scenario chỉ khác cách diễn đạt.

---

# 5. Output

Tạo danh sách Scenario theo cấu trúc:

| ID  | Module | Requirement/UC/API | Test Scenario | Category | Cơ sở từ tài liệu | Priority |
| --- | ------ | ------------------ | ------------- | -------- | ----------------- | -------- |

Trong đó:

### ID

Đặt:

SC-001
SC-002
SC-003
...

### Test Scenario

Viết ngắn gọn, rõ ràng, thể hiện **một mục tiêu/tình huống kiểm thử**.

Ví dụ:

- Kiểm tra đặt xe với thông tin hợp lệ.
- Kiểm tra đặt xe khi thiếu điểm đón.
- Kiểm tra đặt xe khi không có xe khả dụng.

Không viết thành Test Case chi tiết.

### Category

Có thể sử dụng:

- Functional
- Positive
- Negative
- Boundary
- Missing Data
- Error Data
- Authentication
- Authorization
- Business Rule
- Data State

Có thể có nhiều Category.

### Cơ sở từ tài liệu

Ghi rõ Scenario được suy ra từ:

- Requirement nào
- UC nào
- API nào
- Validation nào
- Business Rule nào

### Priority

Chỉ sử dụng:

- High
- Medium
- Low

Priority phải dựa trên mức độ quan trọng thể hiện trong tài liệu nếu có.

Nếu không đủ cơ sở để xác định Priority:

> Cần xác nhận

Không tự đánh giá tùy ý.
